## 35. 2V2「狩猎模拟」与配套改动

维护者的决定（2026-10-16 / 2026-10-17）：在上游的 1–4 人合作之外，加一个**2V2 对抗模式**——两支双人小队共享一个时钟、
各自为战，休整期后进入**狩猎期**（上游叫「对抗期」，本作改名）给对面派猎物，并在同一场模拟里比谁打得更好。模式本身
外加一批客户端 / 服务端的便利改动。`docs/design/` 的规范行相应更新（§6.1、§5.1）。

### 35.1 The 2V2 room model (teams, one HP pool, per-team setup)

- **Three room modes** (`shared/constants.js ROOM_MODES`): `solo` / `coop` / `versus`。`versus` = 2V2：`TEAM_SIZE` 2、`TEAMS`
  2，座位 0、1 → 队 0，2、3 → 队 1（`teamOfSeat`）。房间的模式是 `room.mode`，`Match.isVersus` 派生（`server/match/Match.js`）。
  除房间模式本身外，游戏数据仍用多人的调参：`data/config.json` 是生成的（AGENTS.md 禁止手改），所以 versus 的增量（两队、
  竞争机制）写在代码里（`modeIdFor` 对 `versus` 用 `mode_multi_*`；`server/lobby.js` 与 `server/match/**`）。
- **固定 2v2，空位补 AI**：开赛时每个空位交给一名 AI 队友（`server/lobby.js _fillEmptySeatsWithBots`），两个人（甚至一个人）
  也能开局。房主可在等待室拖动头像**交换座位**，队伍随座位走（`room.swapSeats`，`public/js/screens/room.js` SeatCard）。
- **共享生命池**：每队只有**一条**目标生命值 = 两名成员所选策略的初始生命值之和（`MatchInfra.initTeamHp`，`m.teamLps`
  `Map<teamId, hp>`）。扣血落在池子上，成员各自的 `ps.lp` 只是它的拆分（Σ = 池），UI 显示池本身（`m.public.teamLps`；
  `_teamLpLoss` / `_syncTeamLp`，`server/match/match/bossRounds.js`）。一队同生共死——没有「单人被淘汰」的状态，这也是
  狩猎期一对一配对能成立的原因。漏怪仍按人结算（每人每回合 `min(lpCapPerRound, counted)`），扣的是整队的池子
  （`server/match/match/settle.js`；`lpCapPerRound` 10，`server/match/gamedata.js`）。
- **一队一套配置**：每队有自己的 5 个被禁核心盟约（8 个里禁 5、留 3 可用）与各自的公共棋池（`Match` 构造器：`pools` /
  `teamBans`）；机变每队 4 张、两队轮流各取 1 张（每队拿 2 张；双方同一家族、同一固定梯度：悬赏 I×2+II×1+III×1、
  补给 低×2+中×1+高×1、战术 团队×2+个人×2；机密商店保持官方 3 张抽取），`match/spDraft.js`）；「重刷本局」按队各投各的、只改本队禁用的核心盟约
  （阶段 / 领袖共用，`server/match/match/setupVote.js`）。机变与禁用的可见性也按队（`messaging.js _teamPublicView`）。
  **重刷投票的计时（改自上游 0.2.3 §28.21 的「暂停 + 禁止确认」）**：投票期间确认本局信息仍可提交（只推迟阶段推进），
  倒计时一直可见——投票独占**整整一段**本局信息窗口（不是剩余时间），拒绝 / 取消 / 掉线 / 离开退回被打断的剩余时间，
  无人应答则窗口到点放行（绝不空转）。`test/match/setup-reroll.test.js`、`setup-reroll-ws.test.js`、`versus.test.js`。
- **对抗起始回合**：每局从 R4 / R5 / R6 里用种子 rng 抽一个（`Match.contestStartRound`，`m.public.contestStartRound`）。
- **信息窗口**：确认本局信息 45 秒（`VERSUS_INFO_SECONDS`；全员就绪仍可提前结束）。
- **开发补偿**（设计 2026-10-16）：从对抗起始回合起，**每隔一回合**每名存活玩家得到 1 个「简易通讯机」
  （`VERSUS_ITEM_PHONE` `chess_item_2_06_e_a`）；某队共享池**首次**跌破 `VERSUS_LOW_LP` 21 时，该队每人得到 1 个
  「寻呼模块」（`VERSUS_ITEM_PAGER` `chess_item_4_01_e_a`，整局每队最多一次；`match/prep.js _versusPrepGrant`）。
  [ASSUMED] 补偿尊重共享道具池（`canGain`），耗尽时静默跳过。
- **掉线与离开**：断线保留座位、10 分钟内可回座（`platform.js onDisconnect`）；**中途退出（放弃模拟）在 versus 里交给
  AI 托管**而不是按淘汰处理（`platform.js onLeave`：`ps.autoplay = true`，席位满员，一对一配对不受影响，
  播报「已离开，AI 接管」）。solo / coop 保持原规则。
- **对手在 R13 之后可见**：`messaging.js _teamPublicView` 在 `Match#opponentRevealed` 为假时把对手的行改成 `hidden: true`
  的存根（仍带本队共享池，便于两侧都画出血条），并丢掉对手的 field / 联防 / 草稿条目；R14（`opponentRevealed(round)`
  = `round > VERSUS_CONFRONT.huntRound`，即 R13 最终狩猎之后）起与结算时全部公开，且对手的棋盘 / 关底战场可被观看
  （`watch.js`；客户端 `battle/observe.js` / `gameLogic/watch.js` / `teamPanel.js` 跟随，提示「R13 之后可以看到对面视角」）。
  **观战者（`MAX_SPECTATORS` 2 名）不受任何队伍限制**：`m.public` 自始不含存根、`g.watch` 可看任意玩家 / 战场
  （`Match#isSpectator`）。判定只有一处：`shared/constants.js opponentRevealed(round)`。

### 35.2 The 狩猎期 (the competition layer)

规范：`server/match/match/confront.js`、`server/match/match/confrontTraits.js`、`public/js/ui/confrontOverlay.js`、
`public/js/ui/merchant.js`、`shared/constants.js VERSUS_CONFRONT`、`PHASE.CONFRONT`（`PHASE_NAMES.CONFRONT` = 狩猎期）。

- **何时**：从对抗起始回合到关底回合之前，每个非关底回合的休整期结束后进入（`confrontActive`：`round >= contestStartRound
  && round < gd.bossRound`）。**分两步，双方同步**：
  1. **选目标**（`targetSeconds` 10 秒）：每人指定一名对手；**队内先选先得**，队友拿剩下的那一个，于是四人一对一配对
     （`assignConfrontTarget`）。全员持有目标（或窗口结束）即进入第 2 步（`maybeFinishConfrontTargets`）。
  2. **定制怪物**：每人把自己的**价值预算**填满。这一步**没有独立时长**——窗口就是**本轮休整期的时间**（`gd.prepTime`；
     独立 / `soloUntimed` 时不限时），且只是上限：**全员提交即结束**（`maybeFinishConfront`），超时由 **AI 自动投放**
     （`botConfront`：默认「靠中」、按价值从大到小尽量塞满，先特异、装不下再顺次换类型）。面板上对手以 `?` + 编号显示。
- **替换比例 / 预算**（`confrontRatio` / `confrontBudget`）：起始回合 **5%**（`ratioBase`），每回合 **+2%**（`ratioStep`），
  **上限 15%**（`ratioMax`）；第 13 回合是**最终狩猎**（`huntRound` / `huntRatio`）——固定 **50%**。每人预算 = 本回合波次总价值 ×
  比例 × `budgetMul` 2，**每人各算各的**（个算个的）。**没有数量上限**：只限合计价值（`_confrontMember` 只检查价值与合法性）。
- **分组 = 官方 7 类「特训敌人」**（`confrontTypeGroups`，`data/factions.json types` 的顺序与名称）：特异 / 飞行 / 频次 /
  元素 / 持续 / 隐匿 / 折射。一只怪可同时属于两类（数据里两处都列时两边都出现）；模板位敌人数据里没有类型，手工指派
  （`CONFRONT_GROUP_EXTRA`）。**可跨类型混搭**：`group` 只是显示，`_confrontMember` 只校验所有怪都在「任一类型」里且总价值
  不超预算。玩家点的是**口味（flavour），不是强度**（类型大小不等：特异最大，频次最小）。
- **特性分档**（`confrontTraits.js`）：每只怪按特性分 1 / 2 / 3 档（1 档 ≈ 纯数值、2 档是真机制、3 档改变战局）。
  特性价值是**绝对加项** `step × (grade − 1)`，`step` 每回合按数值缩放标定，使**分档部分恰好占整张价值表的
  `VERSUS_CONFRONT.traitShare` 30%**（`confrontTraitStep`：Σ(step·(g−1)) = share/(1−share) · Σ(stat value)）。飞行**不是**特性
  （按 2 阻挡计入 stat）；**远程怪**（`applyWay === 'RANGED'`）的 stat 价值 **×1.5**（维护者 2026-10-18：能越过阻挡输出），
  标定用的 Σ(stat value) 也含这个倍率，所以特性占比仍是 30%；**频次怪**（`factions.types.TIMES`）的 stat 价值也
  **手动 ×1.5**（用户 2026-10-21，与远程倍率叠加、既频次又远程为 ×2.25，标定同样含这个倍率）。
  ——它已在 `confrontValue` 里按 2 个阻挡位计价。120 只池内敌人：27 档 1 / 53 档 2 / 40 档 3；不在表里的一律读作档 1
  （`test/match/confront-traits.test.js` 保证表的完备性）。特性评审 2026-10-17（4 名评审 + 一致性复核）。
- **价值公式**（`confrontValue`）：`hp + atk×2 + def×2 + res×15 + max(0, lpr−1)·hp·0.6 + blocks×60`，`scale` 用本回合的
  hp/atk 倍率（`gd.enemyScale`），使「一张卡的价值」与「本回合波次价值」同一单位。
- **投放如何生效**（`applyConfront`）：一名玩家的怪只落在**他锁定的那名对手**的波次上（`confrontFor`）；对方波次里
  随机替换掉价值约 `share × 波次价值` 的原怪（误差 2% 以内），插在选定位置（`_confrontInsertTime`：靠前 / 靠中 / 靠后 =
  怪物数的 25 / 50 / 75%）。每只怪带 `countInTotal: false`——**漏过不扣目标生命、也不破坏完美作战**（该标志同时驱动
  LP 扣费与完美作战计数），所以只有击杀有意义。
- **击杀赏金**（`confrontBounty` / `confrontBountyOf`，`VERSUS_CONFRONT.bountyCaps` / `finalHuntBounty`）：只算**对面投放的怪**，
  按**击杀比例** `floor(上限 × 被清 ÷ 投放)` 结算——第 1–4 次狩猎期固定 **1 / 1 / 2 / 2**，第 5 次起按
  `Σ 被清投放怪价值 / 本回合波次总价值 × 本回合资金 × killIncomeShare` 实时结算，R13「最终狩猎」固定 **25**（同样按
  比例折算，全清 25、杀一半 12）。**没有逐只保底**；分母只数投给这名玩家的投放怪，普通波次怪不计。赏金经 sim 的
  `bounty` 机制发放（`server/sim/battle/economy.js _bountyPayee`）：**击杀者获得**（联防里帮忙的队友也算）；没人能算作
  击杀（地形烫死、自己掉血、其他敌人等）时，归**波次的主人（被投放方）**。
- **赏金 ≠ 金币**（商人「坎诺特」）：投放怪的赏金**不进金币**——`deploy.js` 见到 `bounty.bank` 只调 `addBank`
  （`pp.bank`，事件 `['bank', …]`），战报的每名玩家条目带 `bank`（`b.result`，`fields.js` 按 `spec.bounds.bankCoins`
  校验 `bank ≤ Σ 投放赏金` 且 `coins + bank ≤ Σ 全部赏金`，防作弊），`settle.js` 把它加进 `PlayerState.bountyBank`——
  **跨回合留存、重连不丢**，只有一局结束才清空。官方的「悬赏」卡不带 `bank`，仍进金币。赏金→金币的**唯一通道**是休整期
  在**金币卡上方的坎诺特头像**（`ui/merchant.js`，头像取策略「坎诺特」`band_cannot` / `icon_cannot`）处取钱：
  `g.confront.withdraw { gold }`（`Match.withdrawBounty`，服务端权威），比率 `merchantRates` 按**绝对回合**（R1–R8 20%、
  R9 30%、R10–R14 每回合 +5%、R15 100%），成本 `gold / rate`，**每回合第一次向上取整、之后向下取整**，普通回合每回合
  最多 4 金（`merchantRoundCap`）、R15 不限（`merchantUncappedRound`）；余额 / 回合上限 / 阶段 / 已准备一律由服务端拒绝
  （`ERR.MERCHANT_BANK` / `ERR.MERCHANT_CAP` / `ERR.WRONG_PHASE` / `ERR.ALREADY`）。私有视图 `m.private.merchant` 带
  `bank / rate / cap / left / options[{ gold, cost, enabled }]`，公开的 `players[]` 也带 `bank` 与 `rate`。
- **显示**（`public/js/ui/confrontOverlay.js`）：队列里每只怪**默认下路**，**点一下换门**（上路 / 下路），**长按住
  这一行拖动**可排序（380 ms 长按）；「**自动选择**」按价值自动塞满（跨类型）、「**沿用上轮**」按本机记忆的种类重新装填
  本回合预算（模块级 `lastSquad`，刷新页面仍在）。提交后进入各自的等待。**对面投放给你的怪**在战场上带一圈**淡红描边**
  （`render/units.js` `0xff9a86` ring）并标出 `P<n>` 来源座位——**只是显示**（`info.js confrontSeat`，不影响漏怪计费）。
- **悬赏名单**（`ConfrontClash`）：狩猎期一关（双方锁定、即将开战），**双方的名单都公开**——逐条「攻击者 → 一组怪图标 →
  目标 `?`+编号 → 赏金 +N」，约 5.2 秒后自动消失（显示用）。狩猎期**运行期间**对手的目标 / 提交仍被隐藏
  （`_teamPublicView` 只保留本队条目），这份名单是最终攻势前唯一能看到对手阵容的地方。
- **事件期 boss 格**（user 2026-10-21）：**只在事件期回合**（`match.eventRounds` = E1 / E2 / R13，R4 起始即 R4 / R8 / R13）
  的定制面板多出**第 5 格 boss**（R13 是 7 类 + boss = 8 格，其余事件回合 4 类 + boss = 5 格；`views.js`
  `confront.bossPool = [{ key, name, coin }]`，其余回合为 `null`）。池子 = **机变悬赏卡池里所有会出现的怪**
  （`data/choices.json bountyDrafts` initial / boss / hunter 各组 cards 的 `enemyKey` 与 `adds[].enemyKey` 去重，约 81 只，
  `confrontBossCoins`），每只怪的金币 = 它在**所有卡（含 adds）**里出现过的 `coin` **最高档**（8 只多档，如 2 / 1 / 3 → 3）。
  boss 选中后照常**投放给对面**，但**只能排在波次最后入场**（`_confrontBossSpawns`：[ASSUMED] 所有 spawn 的
  max(time) + 10 起、逐个 +1）；**上限 = 第几次事件**（`confrontBossCap()`：E1 1 个 / E2 2 个 / E3 3 个，用户 2026-10-21
  测试后修订，选满置灰并自动返回主界面；协议仍以 `VERSUS_CONFRONT.maxBosses` 32 为列表上界），**同一轮每个
  选项至多选 1 次**（同一提交内 enemyKey 不得重复 ⇒ `ERR.CONFRONT_COUNT` [ASSUMED]；每轮重置、跨轮可重复），**不占投放
  预算、不计 maxPicks**（`picks` 可为空，只投 boss 合法；boss 也**不替换**原怪 [ASSUMED]）。击杀**直接给金币**
  （`bounty { coins: 池金币, bank: false }` → `economy.js addCoins` → 下回合 `pendingFunds`，击杀方收款），**不进坎诺特
  赏金账本**；漏掉不给。协议 `g.confront.bosses` **可选**（旧客户端不发照常工作）。**AI / 托管不用 boss 格**
  [ASSUMED]（`botConfront` 保持确定性），**同盟狩猎不加**（仅 `isVersus`）。

### 35.3 The 2V2 boss chain (R14 / R15)

- **配对在队内**：关底配对只在**同队两人之间**形成，对手永远不共用一个战场（`bossPairGroups`；配对本局固定，R15 沿用，
  `bossWaves`）。同队两人共享一个关底战场、一人守左半边、一人守右半边。
- **各打各的 Boss**（设计 2026-10-16）：每队一条独立领袖血条 / 池（`startFinalAssault`：`this.bossPools` 每队一条，
  血量 = `bossPoolHp(gd, bossId, 本队开战时存活人数)`），`m.public` 的 `b.pool` 每队一条（标量 `hp` 为 `null`）。一队的
  进度不影响另一队。
- **结束与胜负**：每队池子归零记该队 `cleared`、本队共享池归零记 `forced`（`_checkFinalEnd`，逐队记录）；两队都有结局时
  整局结算。`_versusDecide` 先比每队两场领袖战的**剩余时间占比**（user 2026-10-17）：第 14 回合最终攻势按 **4** 份、
  第 15 回合隐秘核心按 **5** 份，`4 × R14 剩余 / R14 时限 + 5 × R15 剩余 / R15 时限`（按各轮自己的倒计时折算，
  **没打到的回合按 0 计**；剩余时间在该队这场领袖战结束的那一刻记入 `bossTeamTimes`，跨轮不覆盖）。时间分高者胜；
  时间分相同再比剩余生命池，仍相同才用原来的「打掉自己血条的比例 → 剩余生命池 × 2 秒 + 剩余时间」折算分，
  分出 `winnerTeam`（全同分为 `null`，`versusOutcome.timeTie` 记录「时间同分」）。**双败**：一队在最终攻势前被全灭
  则两队都不通关（`settle.js afterSettle`，`versusOutcome.doubleLoss`）。玩家 `victory` 随本队胜负（`results.js`）。
- **隐秘核心（R15）门槛（2V2）[ASSUMED]**：按**队**判定（`_bossChainEligible`：本队存活成员的激活层数总和
  > `hiddenCore.multi × TEAM_SIZE / 4` = **600**，且本队池 > `hiddenCore.minTeamLpExclusive`）；因为回合是共享的，
  **任一队达标**即可进入（两边都要求会让隐秘核心基本不可达）。合作模式仍是官方的 4 人门槛 1200（`hiddenEligible`），
  标准模拟没有 R15。
- **本作没有第三关：boss 链止于隐秘核心（R15）**（user 2026-10-17：R16「终焉核心」**整块删除**，不是搁置）。原先搁置用的
  总开关 `THIRD_BOSS_ENABLED`、规格常量 `VERSUS_THIRD_BOSS` 与全部派生代码（`gamedata.hasThirdBoss`、`roundCfg` / 血池 /

### 35.13 Event period (the 16 hunting wordings)

- **是什么**（维护者 2026-10-17 定稿）：一局 **3 次**、每次**四选一**的局内词条抽取。目标池是**对面 A / 对面 B / 队友 / 自己**，**同一目标一局只能用一次**；三次落在约 R4 / R9 / R13 的**休整期之前**，最后一次带进 R13 最终狩猎与 R14 最终攻势。
- **为什么是这个结构**：
  - 「自由选目标 + 每局 4 次」被**支配问题**否掉：按最初的三张概率表（自己与队友的期望同为 0 / +3%），**「给自己」被「给队友」严格支配**，理性玩家不会选自己，四选一实际只剩三个选项（`local-ext/` 的事件期可行性评审稿 §一）。改成「3 次 + 目标不可重复 + 自己幅度 ×2」后，支配问题变成**顺序**问题：三个目标必然不同，自己那一格是高方差赌博而不是劣选项，强度上限也被锁在 3 条词条。
  - 次数从 4 降到 **3**：14 个回合 × 4 人 × 4 条词条会让总增强盖过盟约（标定稿 §8 的占比表）。
- **概率与幅度**（用户原表）：自己 30% 减 / 40% 中性 / 30% 增、**幅度 ×2**；队友 10 / 50 / 40；对面 40 / 50 / 10（「增」= 利好对面，是真赌博）。**中性不是「无效果」而是「交换型」**（攻击换攻速、生命换攻击），否则 40–50% 的中性会变成空转。
- **词条池**：**16 条**（输出 / 生存 / 经济 / 位置各 4 条：2 增益 / 1 减益 / 1 交换），全部围绕狩猎命名——磨刃 / 追风 / 钝口 / 重弩 / 猎人披挂 / 营地篝火 / 血痕 / 轻装远行 / 猎人佣金 / 赏金嗅觉 / 空手而归 / 集市换货 / 鹰眼 / 轻捷 / 陷足 / 陷阱布置（`local-ext/事件期-词条池-狩猎主题.md`）；名称本身就是 i18n 的 msgid，四个语言包照狩猎意象翻译，不使用任何外部作品的品牌词。
- **数值按引擎单位逐条标定**（`local-ext/事件期-强度标定.md` §0.1），不统一 ±10%：攻速是**加法点数**（`mods.aspd`，`units.js` 的 `interval = bat·100/ASPD`）、射程是**整数格**（`rangeExtend` 被 `Math.round()`）、经济类必须用**固定金**（资金全程 `Math.trunc`，±5% 恒等于 0）。取值：磨刃 +13% / 追风 +12 点 / 钝口 −6% / 重弩 +13% −12 点 / 猎人披挂 +25% / 营地篝火 +6% 最大生命每秒 / 血痕 +8% / 轻装远行 +25% −7% / 猎人佣金 +2 金 / 赏金嗅觉 +2 金每次 / 空手而归 −2 金 / 集市换货 刷新 −1（每回合 2 次）、出售 −1（最低 0）/ 鹰眼 +2 格 / 轻捷 上场 +1 / 陷足 敌方移速 +15% / 陷阱布置 +2 格 −12 点。
- **强度目标**：一局 3 次的**期望总增强 ≈ +25%**（≈ R13 时 220–280 层盟约），在构筑占比里是第二大支柱（约 20%，低于盟约、高于装备）。护栏：期望 ≤ +25%、p5 ≥ +10%、单期最差 ≥ −8%、不做「再给一张」的连锁。
- **与已有系统的关系**：词条与盟约 / 装备 / 技能**同属一个加法池**（`units.js` 的 `Σpct`），所以高层数的板吃词条更少，天然抑制「强者更强」；经济类词条只动**资金**（收入 / 刷新 / 售价）与**投放怪赏金**，**不碰坎诺特的取钱比率**，避免和 §35.2 的赏金曲线相乘。
- **确定性**：抽取走服务端的种子 rng；golden 场景不进事件期（事件在被测对局里为空），`npm run golden` 不变。
- **公开**：谁拿了哪一条、加在谁身上**双方都可见**（避免和「对手在 R14 前不可见」叠成信息差）；AI 队友与托管的座位自动选，超时按期望最高的目标。
- **状态**：**已实现**（`server/match/match/event.js`、`public/js/ui/eventOverlay.js`、`public/js/ui/roundBuffs.js`；测试 `test/match/event.test.js`、`test/ui/event-ui.test.js`）。合作版「同盟狩猎」由系统投放，目标为自己 / 队友。

### 35.15 猎手 AI（the AI 狩猎模式，2026-10-25）

2V2 里由 `botControlled` 座位（AI 队友、AI 托管、掉线与超时的自动决策）发出的狩猎投放不再是「只顾自己预算的贪心填充」，
而是**回应它瞄的那个玩家的上场阵容**（维护者 2026-10-25 定名「猎手 AI」，方案 A）。它只改**选择**，不改**资源**：
预算、候选池（本局共享的类型卡与 `confrontValueOf` 价值表）、`maxPicks`、boss 格上限 `confrontBossCap()`、上下门与插入
时点的合法域全部与真人一致；方案必须通过真人 `g.confront` 用的同一道闸门 `confront.js _confrontMember`，被拒就退回
0.0.4 的贪心填充——因此「AI 偷偷超预算 / 用不存在的怪」在结构上不可能。

四个决策面，按重要性：

1. **打谁**（`aiHunterTarget`）：把每个可用对面座位按「我方这套怪最能动他哪里」排序，加上「场上棋子少」的压制加权
   （他越少越难回应），从反制排名的前 `width` 名里取；只有唯一候选时不掷随机（不消耗随机流）。取代过去
   `assignConfrontTarget` 的「取第一个空位」。
2. **打什么**（`aiHunterPlan`）：对候选池里每只怪算 `counterScore = Σ(特性权重 × 该特性的短板度)`，按
   `(score + 1) / value` 的性价比排序后取（先不重复地铺 breadth，全部不可负担后才重复同一答案）。特性只读数据本身：
   `isFlyEnemy`/`acTypes(FLY)`、`applyWay==='RANGED'`、`acTypes(INVISIBLE / TIMES / DOT / ELEMENT / REFLECTION / SPECIAL)`、
   `stats.def / res / atk / hpRecoveryPerSec`、`summons`，以及既有 特性分档表 `confrontTraits.js confrontTraitGrade`。
   每条权重指向一条引擎规则：飞行要 `canHitFly`、**隐匿在被阻挡后即可被选**（`server/sim/targeting.js`）所以缺阻挡怕隐形、
   高甲怕法伤、高法抗怕物理、频次 / 自愈 / 召唤怕缺单体爆发、反射反而惩罚单点高爆发、特性 3 档惩罚阵容单薄。
3. **什么时候到**（`aiHunterPosition`）：`front`＝波次 25 %（目标场上棋子少，抢在成型前压）、`back`＝75 %（目标有墙 / 有
   回血，等它把阻挡与技力耗掉再压）、否则 `mid`；`weak` 档只允许 `mid`（与 0.0.4 同）。
4. **boss 格**（`aiHunterBosses`，K3）：**只有最强档**用，仍受 `confrontBossOpen()` / `confrontBossCap()` / 每份投放内
   同名怪只能点一次 的约束，且不占预算、金币仍归击杀方。这作废了 2026-10-21 的 [ASSUMED]「bots / 托管从不点 boss」。
